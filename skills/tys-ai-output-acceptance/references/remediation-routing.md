# 修复路由

只在出现未通过或关键项未验证时读取。先识别主要原因，再推荐最小动作；不要用工具名称代替因果解释。

| 主要原因 | 优先修复动作 | 可用能力 | 复测证据 |
| --- | --- | --- | --- |
| 目标错误或含混 | 回到目标拆解，重新确认使用者、任务与期望状态 | 用户确认、目标用户访谈 | 新目标和验收标准获得明确确认 |
| 验收标准缺失 | 把形容词改写成行为、边界和禁止项 | 需求清单、样例、决策人 | 每个关键要求有可观察条件 |
| 信源不存在、过期或不支持主张 | 删除无依据主张，或改用原始、权威、当前适用的来源 | 网页检索、数据库、知识库、适用的 MCP 或连接器 | 原文逐条支持主张，日期和范围适用 |
| 当前工具无法访问所需证据 | 发现能直接取得证据的现有工具；必要时建议连接对应服务 | MCP、应用连接器、浏览器、文件读取、测试环境 | 工具返回可追溯原始记录，而非模型转述 |
| 模型能力或上下文不匹配 | 补充必要上下文、拆小任务，或选择更适合该任务和工具调用的模型 | 长上下文模型、推理模型、视觉模型、代码模型 | 新产出重新通过原验收步骤 |
| 需要发现反例或遗漏 | 使用另一模型或多角色审核生成质疑清单 | 第二模型、多模型并行、对抗评审 | 每条质疑再由来源、工具、运行或专家核实 |
| 实现缺陷 | 用失败复现定位最小修改 | 代码编辑、测试、日志、调试器 | 原失败场景通过，关键旧路径无回归 |
| 环境或配置错误 | 固定版本、依赖、权限和配置，在等价环境复现 | 沙箱、容器、测试账户、环境诊断 | 目标或等价环境中重复获得相同结果 |
| 缺少真实用户反馈 | 设计最小用户任务或小范围试验 | 原型、可用性测试、A/B 测试 | 预先定义的行为指标达到通过线 |
| 超出用户和 Agent 的专业能力 | 整理问题、证据和未决项后转交合格专业人员 | 医生、律师、会计师、安全人员等 | 有资格且承担责任的人完成复核 |

## 推荐 MCP、连接器或工具时

1. 先写清缺少的证据是什么，例如“需要读取 CRM 中真实成交记录”，再寻找能访问该证据的能力。
2. 优先使用当前已连接且权限足够的工具。不要假装一个未安装、未连接或不存在的 MCP 可用。
3. 接入会暴露数据、改变外部状态、要求登录或产生费用时，说明范围并等待用户明确授权。
4. 只申请完成当前复测需要的最小读取或写入范围。
5. 工具返回结果后仍检查来源、时间、对象和版本是否匹配。

## 推荐切换或调用模型时

只有模型确实构成失败原因或能显著降低查漏成本时才推荐。说明模型承担的角色：重新生成、视觉检查、代码分析、长文档读取、反例生成或批判审核。

- 不用“更强模型”作为没有标准的万能建议。
- 不把模型自评、投票或多数一致当成真实性证明。
- 新模型改出的结果必须重跑同一套验收标准。
- 涉及敏感材料时，先确认数据是否允许发送给该模型或服务。

## 修复优先级

1. 先处理会阻止当前用途的关键失败；
2. 优先可逆、低成本、能产生独立证据的动作；
3. 一个动作能同时修复多项同源失败时优先；
4. 证据不足时先补证，不在未知原因上反复生成；
5. 高风险或不可逆问题优先转交专业复核。
