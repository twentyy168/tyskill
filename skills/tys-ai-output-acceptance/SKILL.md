# AI 产出验收

## 任务

把一个“看起来像完成了”的 AI 产出，转化为有目标、有证据、有边界的验收结论。它服务两类用户：非程序员通过可观察结果参与验收；程序员通过命令、测试、日志和代码位置参与验收。两种模式共享同一证据标准和风险边界。

## 核心定义

- **AI 产出**：AI 生成或修改的文字、代码、文件、数据分析、设计、方案、自动化或外部动作结果。
- **可用**：产出在指定情境中达成目标、满足关键约束、风险可接受，而且有足够证据支持。
- **验收**：把产出与目标、约束和现实证据比较，而不是让生成者评价自己。
- **独立证据**：来自原始来源、确定性工具、实际运行、目标用户、现实结果或合格专业人员的证据。

AI 自称正确、同一模型自查或多个模型意见一致，只能产生待核实线索，不能单独构成通过证据。

## 不变量

1. 先拆解用户真正要达成的目标；用户确认验收标准后，才检查产出。
2. 验收目标、产出版本和测试环境必须对应；不拿旧版本证据证明新版本。
3. 把复杂产出拆成事实、计算、行为、约束、判断和外部动作，分别选择证据。
4. 验收强度随错误代价提高；低风险可以抽查，高风险必须使用更强证据或专业复核。失败代价不能只有低／中／高评级，必须描述具体后果、受影响对象、发生条件、影响范围和可逆性。
5. 只检查当前证据能支持的范围，不把“没发现问题”写成“已经证明正确”。
6. 交互深度随用户的技术能力变化，但不降低证据标准；同一项不能因用户会或不会编程而获得不同结论。
7. 验收请求默认只授权检查。未通过时必须给出可执行的修复方案；除非用户同时要求并授权修复，否则不连接外部服务、不切换工作环境、不修改产物、不发布、不发送、不付款、不删除。

## 开始条件

优先从对话、附件、工作区和已有测试恢复信息，不重复询问。至少需要：

- 待验收的产物或可访问位置；
- 它要服务的使用者和具体目的；
- 已知的关键要求，或足以推导最低要求的情境。

缺少目标或待验收产物时，请用户补充后停止。只有一个缺口会实质改变目标拆解、验收方式、权限或高风险结论时，才问一个合并后的问题。低风险细节可以透明假设，并在目标草案中标明，等待用户确认。

## 选择交互模式

优先使用用户明确表达的身份、期望交付和已有材料判断：

- 用户说明自己不会编程、提供截图或只要求检查“能不能用”时，使用**非程序员模式**；
- 用户提供代码、命令、测试输出、堆栈或明确要求技术细节时，使用**程序员模式**；
- 仍无法判断时，默认非程序员模式，并用一句话允许用户切换：“如果你需要命令、日志和代码位置，我可以改用程序员模式。”

模式只改变沟通和协作方式，不改变是否需要独立证据、风险控制和外部动作授权。

## 非程序员交互原则

- 能由 Agent 读取文件、运行测试、检查日志或调用工具完成的技术动作，由 Agent 直接完成。
- 需要用户操作时，只给可见界面中的最短步骤，并说明应观察什么、回传什么；不得只丢给用户一串命令。
- 技术证据先保留原始位置，再翻译成“发生了什么、影响什么、是否阻止使用”。
- 不用“你不懂技术”降低标准，也不让术语数量冒充验收深度。
- 用户想借验收过程学习编程时，可以解释相关概念；纯教学需求不属于本 Skill。

## 程序员交互原则

- 先识别语言、运行环境、依赖、测试入口、配置差异和可复现路径；不要求用户重复已经提供的技术上下文。
- 可以直接给出命令、断言、日志片段、请求与响应、文件位置和最小复现步骤；每一项都要说明它验证了什么，而不是罗列输出。
- 优先复用项目已有的测试、lint、类型检查、构建、集成测试和可观测性；缺失时再提出最小补充测试。
- 区分“测试失败”“测试未覆盖”“环境无法复现”和“实现违背需求”，不要把它们都叫 Bug。
- 用户只授权验收时，允许只读检查和安全的隔离测试；不改代码、不执行迁移、不部署、不清理数据。用户明确要求修复后，才提交最小修改和回归测试。
- 即使程序员能够阅读代码，仍要用端到端行为、权限边界和真实环境证据检查关键需求；代码审阅不能替代验收。

## 工作流程

### 1．目标拆解

先把用户口中的“做出来了”“能不能用”“看一下对不对”拆成：

```text
目标使用者：谁要使用或受影响？
真实任务：他要完成什么行动？
决策与时机：若产物要推动购买、报名、预约或咨询，目标对象为什么应选择它，又有什么真实理由现在行动？
期望状态：完成后世界发生什么可观察变化？
交付产物：AI 具体生成或改动了什么？
关键约束：时间、成本、格式、权限、风险或边界是什么？
失败代价等级：低／中／高
具体失败后果：错了会发生什么，而不是只写“有风险”？
受影响对象：哪些人、资金、数据、系统、业务或声誉会受影响？
发生条件与范围：在什么情况下发生，影响一次、部分用户还是持续扩散？
可逆性与恢复成本：能否撤回、回滚或补救，需要多少时间、费用或专业介入？
评级理由：为什么据此判为低／中／高？
```

不要把“用户说满意”“界面看起来正常”当作目标。没有可观察的期望状态时，只能先形成目标草案，不能进入验收。

### 2．与用户确认验收标准

基于目标拆解，生成一份简短的验收标准草案：

```text
必须通过：
绝不能发生：
验证环境：
每项的证据方式：
每个关键项失败时的具体代价：
购买／行动理由与时机（销售型内容适用）：
不在本轮验收范围内：
```

将草案发给用户确认或修改。用户已经在当前对话明确确认过相同标准时，引用该标准并视为已确认；否则必须等待明确确认，不能自行把草案当作用户认可的标准。

确认前允许阅读必要材料以识别产物和风险，但不得运行测试、查证关键主张、给出通过或未通过结论，或开始修复。确认后将草案固定为验收契约：

```text
产物及版本：
交互模式：非程序员／程序员
目标使用者：
要完成的任务：
必须通过：
绝不能发生：
使用环境：
失败代价：
- 等级：低／中／高
- 具体后果：
- 受影响对象：
- 发生条件与影响范围：
- 可逆性与恢复成本：
- 评级理由：
```

把“专业、好看、稳定、准确”等形容词改写为可观察条件。若目标本身无法观察，先缩小为本轮能检查的代理结果，不假装已经验证最终价值。

销售型内容要把“为什么选择”与“为什么现在行动”分开验收。前者是目标对象、问题、方案与代价之间是否匹配；后者只能建立在真实、可核验的时间、名额、价格、风险窗口或外部事件上。没有真实时机理由时，不能用虚假稀缺、伪造倒计时或暗示即将失去机会来替代。

失败代价要使用当前任务中的具体名词和可观察结果。例如不要只写“高风险”，而要写“若把未付款用户误标为已付款，会造成订单放行和资金损失；影响全部命中该重试路径的订单；可通过冻结发货与对账补救，但需要人工核查”。无法估算金额或人数时可以明确写“规模未知”，但不能省略后果链。

### 3．拆分验收对象

逐项识别：

- **事实**：人物、日期、数字、引用、法规、研究结论；
- **计算**：公式、金额、比例、统计或数据转换；
- **行为**：点击、提交、保存、登录、调用、自动化执行；
- **约束**：格式、权限、隐私、安全、合规、禁止项；
- **判断**：文案、设计、策略是否适合特定对象；
- **决策行动**：购买、报名、预约、咨询或其他行动理由，以及行动时机是否真实；
- **外部动作**：发送、发布、付款、删除或改变真实系统状态。

一个要求包含多个对象时拆开，不用一个笼统分数掩盖局部失败。

### 4．匹配证据

需要选择具体协议时读取 [验收协议](references/verification-protocols.md)。基本映射是：

| 对象 | 优先证据 |
| --- | --- |
| 事实 | 原始来源逐条对应，必要时交叉核对 |
| 计算 | 独立重算、边界值和反例 |
| 行为 | 在目标环境实际运行，保存输入、步骤和结果 |
| 约束 | 确定性规则、权限检查、安全检查或合规清单 |
| 判断 | 明确评审标准、目标用户测试或小样本现实试验 |
| 销售型决策行动 | 核对价值主张、目标用户反馈与真实时机依据；没有依据时不接受紧迫性主张 |
| 高风险专业结论 | 合格专业人员复核 |

优先使用成本最低且足够独立的证据。多模型审核只能用来发现遗漏、生成反例或安排检查顺序。

### 5．执行验收

在当前工具、文件和授权范围内尽量实际检查，而不是只给建议：

1. 固定产物版本、环境和关键输入；
2. 先检查最关键、失败代价最高的要求；
3. 对正常路径、关键边界和至少一个失败路径取证；
4. 记录实际结果、证据位置和未覆盖范围；
5. 无法直接操作时，给用户最短的界面操作步骤，并说明需要观察和回传什么证据；只有确实没有界面路径时才提供命令，并逐项解释。

测试本身可能发送消息、写入生产数据、付款、删除或公开内容时，不执行；改用测试环境、模拟数据或等待用户明确授权。

### 6．形成结论

每个要求只能是：

- **通过**：有与当前版本和目标环境对应的独立证据；
- **未通过**：有可复现的失败、冲突或不满足证据；
- **未验证**：缺少工具、权限、材料、真实环境或专业能力。

总体结论只使用：

- **通过**：所有关键要求通过，剩余未验证项不会改变当前用途；
- **未通过**：至少一个关键要求未通过；
- **无法验收**：关键要求仍未验证，现有证据不足以接受或拒绝。

不要用百分制、置信度或“基本没问题”替代证据状态。

### 7．修复与复测

出现未通过或关键项未验证时，读取 [修复路由](references/remediation-routing.md)，先区分目标、标准、信源、工具、模型、实现、环境与专业能力问题。用户只要求验收时，交付可执行的修复方案但不实施；不得只说“优化一下”“换个模型”或“接个 MCP”。

修复方案至少写清：

- 失败证据和主要原因；
- 建议动作以及它为什么能解决该原因；
- 需要的信源、工具、MCP、模型或专业角色；
- 新增授权、账号、费用或数据访问要求；
- 修复完成后必须重跑的原失败步骤与通过证据。

用户明确要求并授权修复时：

1. 用失败证据定位最小修改；
2. 当前缺少必要能力时，先发现已有工具或连接；只有确实需要且用户同意时才安装插件、连接 MCP、登录服务或产生费用；
3. 修改后重跑原失败步骤；
4. 再检查可能受影响的既有通过项；
5. 只有新证据通过，才更新结论。

切换信源、调用另一模型或多模型审核只会产生新的候选与线索，不能自动把未通过改成通过。仍须使用与验收对象匹配的独立证据复测。

## 风险边界

以下情形默认视为高风险：医疗、法律、投资与信贷、人身安全、信息安全、隐私、真实付款、数据删除、公开发布以及影响他人权益的自动化决策。

高风险任务中：

- 不凭模型自查、多模型一致或单一二手来源给出通过；
- 清楚区分技术检查与专业判断；
- 无法获得合格复核时，将关键项标为未验证，总体结论为无法验收；
- 不替用户执行不可逆或影响外部人员的动作。

通过／未通过／无法验收

- 产物版本与环境：
- 必须通过：
- 绝不能发生：
- 购买／行动理由与时机（若相关）：
- 失败代价等级：
- 具体失败后果：
- 受影响对象：
- 发生条件与影响范围：
- 可逆性与恢复成本：
- 评级理由：

## 证据
| 要求 | 方法 | 实际结果 | 状态 | 证据 |

- {具体位置、复现步骤、影响或缺少的证据}

没有失败或关键未验证项时删除“失败与未验证项”和“修复方案”。不要隐藏未覆盖范围，也不要把操作过程写成冗长流水账。

## 停止条件

出现以下任一情况时结束当前轮：

- 所有关键要求已有结论；
- 已形成目标与验收标准草案，正在等待用户确认；
- 缺少待验收产物或唯一关键输入；
- 下一步需要新增权限、真实外部动作或专业复核；
- 验收标准只能由用户或目标受众决定，已给出可执行测试；
- 继续检查的成本明显超过当前错误代价，并已说明剩余风险。
